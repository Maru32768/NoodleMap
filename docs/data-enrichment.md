# 店舗データ補完の方針と手順

本番DBに不足している店舗情報を、スクリプトとLLMで補完する。その後は同じ仕組みで定期的に更新候補を集め、管理者が確認してから反映する。

- 基準データは 2026-11-05 の本番バックアップ (SHA-256 先頭 `403ff074ff8cd76d`、goose version 20)。
- この文書の件数はすべて、基準データを読み取り専用で集計した実測値。費用は推定で、推定と書いてある。
- 調査の入力は本番の公開 API から書き出す。店舗を追加しても手元で更新するものはない。本番への反映は管理画面から少しずつ行う。

## 方針の要点

1. **Web調査は隔離環境のSkillで行う。** Web検索を多用するので、Prompt Injection を受ける前提で組む。隔離環境には秘密情報も本番DBも置かず、出せるのは調査結果のファイルだけにする。
2. **LLMが書いた値を直接DBへ入れない。** 調査結果は隔離環境の外で検証してファイルにし、本番の管理画面に読み込ませて、確認したものだけを反映する。初回補完も継続更新も同じ経路を通す。
3. **食べログは店舗の特定とリンクにだけ使い、値は複製しない。** 同定の主経路は食べログ検索にする。一般のWeb検索は3店中1店しか正しい食べログページに届かなかった。食べログ自体の検索は試した2店とも上位2件に正解があった。店名、読み、日付、リンク、タグの値は公式の情報源から取る。
4. **決定的に処理できるものはLLMを使わない。** 住所の表記統一はWebを読まないスクリプトで行う。リンクの正規形、カタカナからひらがなへの変換は検証スクリプトで行う。
5. **店舗はIDのハッシュで36バッチに分け、1バッチずつ処理する。** 店舗を追加しても他の店の所属は変わらない。既存の値がある店も区別せず処理する。DBの差し替えはしないので、作業中の本番の更新は失われない。

## 利用者が決めること

1は決定済み。2から4はフェーズ0で決める。6の上限額はフェーズ3の開始前に必要。5は初回補完の結果を見てから決められる。

### 1. 食べログをどこまで使うか (決定済み)

[食べログ利用規約](https://tabelog.com/help/rules/)に、自動アクセスやスクレイピングを直接禁じる文言は見当たらなかった。一方で第9条は、提供情報を事前の同意なく複製することと、そのための保管を禁じている。店舗情報の抽出がこれに当たらないとは言い切れない。[robots.txt](https://tabelog.com/robots.txt) は店舗ページと検索ページを `*` に許可しているが、GPTBot と Google-Extended は全面的に拒否している。

**利用者は、食べログの情報を複製しないと決めた。** 食べログは店舗の特定と、その店舗ページへのリンク (`link.tabelog`) にだけ使う。営業時間を公式の情報だけで持つ決定 (`docs/adr/0004-business-hours-from-official-sources.md`) と同じ考え方で、ほかの項目にも当てはめる。

- 食べログで読むのは、同定に使う店名と住所だけ。読み、開店日、閉店の表示、ホームページ欄、公式アカウント欄は値の証拠にしない。
- 値の証拠として認めるのは、公式サイト、公式 SNS、駅ビルや商業施設の公式テナントページ、予約・整理券ページだけ。個人ブログ、口コミ、グルメサイト (食べログ、Retty、ぐるなび等)、Google Maps、OpenStreetMap は証拠にしない。転記や古い情報を含みうるからだ。
- 口コミ、点数、写真は読まない。アクセスは1店ずつ順番に行い、403やCAPTCHAが出たらその店では食べログを使わず、回避しない。

`.claude/agents/shop-researcher.md` と `validate-results.mjs` はこの決定に従っている。Skill はツールの呼び出し間隔を固定できないので、以前の案の「10秒に1回以下」は保証できない。フェーズ3で実際の間隔を確認する。

公式の情報がない個人店は、読みが推定に、開店日が空のまま残りやすい。食べログのリンク以外の提案はすべて個別確認になるので、確認の手間は増える。

### 2. 建物名を住所に残すか

**推奨は残すこと。** 形式は `東京都港区北青山3-5-40 PRYME CUBE表参道 1F` とする。駅ナカや商業施設の店は建物名と階がないと現地で見つけにくい。番地の後ろに情報がある623店のうち375店は階の情報を含む。

### 3. 読みの範囲

既存27件は `手打麺祭 かめ囲` が `かめい`、`らあめん 彩鶏どり` が `らあめん いろとりどり` と混在している。検索は部分一致 (`web/src/features/search/utils.ts`) なので、全体の読みなら `かめい` でも `てうち` でも当たる。

**推奨は店名全体の読みとし、支店名は含めないこと。** 語の区切りの空白は店名に合わせる。既存27件も調査し、情報源のある別の読みが見つかれば提案する。既存の値を置き換える提案には `replaces_existing_value` が付き、一括承認の対象にならない。LLM の推定で既存の読みは置き換えない。

### 4. 店名の表記

試した店では、DBの `中華そば 麦笑` が食べログでは `中華そば 麦笑 本所吾妻橋店` だった。食べログの表記は証拠にしないので、支店名は公式の情報源で確かめる。

**推奨は次の4つ。** 優先順は公式サイト、SNSプロフィール、商業施設のテナントページや予約ページ、現在の値とする。支店名は公式の情報源にあれば含める。`東奔西走/トーホーセーソー` のような読みの併記は店名から外し、読みへ移す。公式が英字併記を正式名として使う場合は残す。

### 5. 閉店日が不明な店の扱い

閉店日は閉店状態の判定にも使うので、消すと営業店に戻る。店舗詳細は閉店日をそのまま表示する (`web/src/features/shops/detail-panel.tsx:285`)。

**`2026-09-22` を仮の値として扱う。** 時刻では区別しない。API は日付だけを返し、編集画面で保存すると時刻は消える。時刻のない7店は、この保存で消えたと推定している。証拠があれば実際の日付へ置き換える提案を出す。既存の値を置き換える提案は個別確認になるので、本当にこの日に閉店した店は確認画面で判断する。

**「日付不明の閉店」を表すフラグは、数バッチの結果を見て決める。** 仮の日付が多く残るなら、列を足して店舗詳細に「閉店 (時期不明)」と表示する。`closed_at` は「遅くともこの日までに閉店」という意味で残すので、閉店状態の判定は変わらない。公開画面の誤った日付を早く直したい場合は、調査を待たずに入れてよい。

### 6. モデルと予算

`shop-researcher` はモデルを指定していないので、実行時のモデルを引き継ぐ。既定は Claude Opus 5.5 とする。フェーズ3の検証で30店の実費と精度を測り、Sonnet 5.5 や Haiku 5.5 で精度が保てるかを比べて、利用者が選ぶ。実行を始める前に上限額を決める。隔離環境に渡す Claude の認証情報には利用上限を設定する。

## 仕組み

```text
信頼する側: export-batch.mjs が本番の公開 API から1バッチ分の batch.json を作る (必要な項目だけ)
        |  batch.json と Skill だけを渡す
        v
隔離環境: /shop-research
  オーケストレーター (Web を読まない): 1店ずつ調査を依頼し、結果をファイルへ保存する
  shop-researcher (WebSearch と WebFetch だけ): 1店を調べて JSON を1つ返す
        |  results/ だけを持ち出す。環境は破棄する
        v
信頼する側: 手元の validate-results.mjs で検証する
  手元の batch.json を基準にする。隔離環境のスクリプトやフラグは信用しない
        |  accepted.jsonl (1バッチ1ファイル)
        v
本番の管理画面 (管理者セッション): ファイルを読み込み、本番の現在値と比べて表示する
  ファイルはブラウザの中で読むだけで、サーバーへ送らない
        |  確認した項目だけ
        v
サーバー: 既存の updateShop が検証して保存する
```

| 置き場所 | 中身 | 実行する場所 |
|----------|------|-------------|
| `.claude/skills/shop-research/SKILL.md` | 調査全体の手順。`/shop-research` と入力したときだけ動く | 隔離環境 |
| `.claude/agents/shop-researcher.md` | 1店の調査ルール。使えるツールは WebSearch と WebFetch だけ | 隔離環境 |
| `.claude/skills/shop-research/scripts/check-isolation.mjs` | 秘密情報や本番データがあれば実行を止める | 隔離環境 |
| `.claude/skills/shop-research/scripts/validate-results.mjs` | 結果の検証と正規形への変換 | 両方。判定に使うのは信頼する側の実行だけ |
| `scripts/enrichment/export-batch.mjs` | 本番の公開 API から調査対象を書き出す | 信頼する側 |
| `web/src/features/shop-enrichment/` | 管理画面の「調査結果を取り込み」。ファイルの解析、本番との比較、反映 | 本番の管理画面 |

Skill、検証スクリプト、バッチ分割、取り込み画面は実装済み。サーバーのテーブルと API は追加していない。

### バッチの分け方

`export-batch.mjs` は店舗 ID の SHA-256 の先頭4バイトを36で割った余りをバッチ番号にする。所属は ID だけで決まるので、店舗を追加しても他の店は移動せず、追加した店が既存のバッチのどれかに入る。

基準データの1,798店では、1バッチあたり平均50店、最小39店、最大66店になった。

| バッチ数 | 平均 | 最小 | 最大 |
|---------|------|------|------|
| 18 | 100 | 83 | 115 |
| 24 | 75 | 60 | 90 |
| 36 (採用) | 50 | 39 | 66 |

36にした理由は2つある。

- **店舗が増える余地を残すため。** バッチ数を変えるとほぼ全店の所属が変わるので、固定する。平均100店になるのは3,600店に達したとき。
- **1回の実行を小さくするため。** オーケストレーターは各店の結果を文脈に持ったまま次の店へ進むので、その費用は店数の2乗に近い形で増える (推定)。失敗したときの損失も1バッチで止まる。

### 隔離環境の条件

| 条件 | 理由 |
|------|------|
| Claude Code のプロセスごとコンテナか VM の中で動かす | [Claude Code の sandbox](https://code.claude.com/docs/en/sandboxing) は Bash などのコマンドだけが対象で、既定では `~/.ssh` なども読める。ネイティブの Windows では効かない |
| 中に置くのは `.claude/skills/shop-research/`、`.claude/agents/shop-researcher.md`、`batch.json`、結果の出力先だけ | 注入された指示で読めるものを、公開情報に限る |
| 認証情報は Claude 自身のものだけにし、利用上限を設定する | 本番のセッション、GitHub、AWS、R2、Google の鍵を置かない。`check-isolation.mjs` が環境変数名と既知のファイルを確認する |
| LAN とクラウドのメタデータ URL へ出られないようにする | 内部のサービスへの到達を防ぐ |
| 1回の実行ごとに環境を破棄する | 途中で書き換えられたファイルを次回へ持ち越さない |
| 持ち出すのは結果の出力先だけにする | 実行ファイルを信頼する側へ持ち込まない |

`check-isolation.mjs` は既知の名前を確認するだけで、完全な検査ではない。この確認は誤って手元で実行する事故を防ぐためのもので、攻撃は防がない。隔離は環境そのもので担保する。

### 実行方法

次のコマンドは、リポジトリの外に作った作業フォルダで実行する。`batch.json`、`results`、`validated` は `.gitignore` の対象外で、リポジトリは公開されているからだ。コマンドの `scripts/` と `.claude/` は、リポジトリへのパスに読み替える。

`export-batch.mjs` は実行のたびに本番の `GET /api/v1/shops` と `GET /api/v1/tags` を読む。認証は要らない。接続先は `--api <オリジン>` で変えられる。

信頼する側で進み具合を確かめる。結果は `results/<バッチ番号2桁>/` に置く前提で数える。

```bash
node scripts/enrichment/export-batch.mjs --progress results
```

1バッチを書き出す。番号は0から35。`--fields` で項目を絞れる。選択なしの全店書き出しはできない。試験の店を指定するときは `--batch` の代わりに `--shop-ids <ファイル>` と `--run-id` を使う。

```bash
node scripts/enrichment/export-batch.mjs --out batch.json --batch 7
```

隔離環境で Skill を実行する。途中で止まっても、同じ引数で再実行すれば結果のない店から続く。

```text
/shop-research batch.json results
```

受け取った結果を `results/07/` へ移し、信頼する側の検証スクリプトと、手元に残した `batch.json` で検証する。隔離環境の Skill は `--rejections-only` を付けて実行するので、`accepted.jsonl` を作らない。管理画面に読み込ませるのは、次のコマンドが手元で作ったファイルだけにする。

```bash
node .claude/skills/shop-research/scripts/validate-results.mjs batch.json results/07 validated/07
```

終了コードは、すべて合格が0、却下ありが1。却下ありでも、合格した店の分は `accepted.jsonl` に出力される。このファイルを管理画面に読み込ませる。

店舗を追加したら `--progress` を実行する。`remaining` が1以上のバッチについて、結果のある店を除いて書き出す。調査と検証の手順は同じで、出力先だけ別にする。

```bash
node scripts/enrichment/export-batch.mjs --out batch.json --batch 7 --skip-researched results/07
```

却下されたまま残った店も結果ファイルがあるので、調査済みとして数えられる。調べ直す店は結果ファイルを消す。

### Prompt Injection への対策

| 想定する攻撃 | 止める仕組み |
|-------------|-------------|
| ページの指示でコマンド実行やファイルの改ざんをさせる | `shop-researcher` には Write も Bash もない。[サブエージェントの `tools`](https://code.claude.com/docs/en/sub-agents) はツールを制限する。Skill の `allowed-tools` は事前承認だけで制限にならないので、使っていない |
| 調査した店の内容で別の店の結果を歪める | 店ごとに新しいサブエージェントを使い、文脈を共有しない |
| 秘密情報を外部へ送らせる | 環境に秘密情報を置かない。`batch.json` は店名、住所、日付、タグ、リンクだけを `SELECT` する。評価、気になる度、座標、食事記録は含めない |
| フィッシングサイトをリンクとして提案させる | リンク種別ごとにドメインと形式を検証する。公式、予約、その他のリンクには `link_needs_review` を付ける。食べログのリンク以外の提案は、項目を問わず個別確認にする |
| 証拠の出所を偽る | 項目ごとに認める `sourceKind` を決め、ドメインと照合する。`tabelog.com` の証拠は `tabelog` だけで、`link.tabelog` にしか使えない。グルメサイトと地図の証拠は種類を問わず拒否する。閉店日と臨時休業は公式の証拠だけを認める |
| 文字列で確認者を欺く | 制御文字、双方向文字、ゼロ幅文字を拒否する。店名、ラベル、メモの URL を拒否する |
| 検証スクリプトや判定フラグを書き換える | 判定は信頼する側のスクリプトだけで行う。結果側の `baseValue` などの未知のキーは拒否し、現在値は手元の `batch.json` から取る |
| 結果の置き場所で信頼する側を攻撃する | `<店舗ID>.json` だけを読み、シンボリックリンクを拒否する。1ファイル64KBまで。受け取ったファイルは実行しない |
| 却下の理由で隔離環境へ文字列を戻す | 却下の記録は店舗ID、位置、固定の理由コードだけにする |
| 細工したファイルで管理画面を攻撃する | 読み込み時に未知のキーと種別を拒否する。証拠の URL は `http` と `https` だけをリンクにする。文字列はプレーンテキストで表示する |
| 不正な値を本番へ保存させる | 保存は既存の `updateShop` の検証を通る。管理者が確認した項目だけを送る |

**機械では止められないものが残る。** 許可されたドメイン上の、もっともらしい誤情報はこの検証を通る。公式を名乗るページが示した別人のアカウントはその例で、`source_unconfirmed` などを付けて個別確認に回すだけになる。検証スクリプトが確かめられるのは、食べログのリンクが自分のページを証拠にしていることだけなので、一括承認できるのはそのリンクに限る。別の店の食べログページをその店のものとして提案された場合はこの判定も通るので、一括承認の範囲はフェーズ3の同定精度で確かめる。最後の防御は確認画面での確認になる。

WebFetch は[ページの原文を返さず、別のモデルが処理した結果を返す](https://code.claude.com/docs/en/tools-reference)。注入の影響を減らす可能性はあるが、公式の保証ではないので防御には数えない。一方で、抽出の誤りが入りうるので、精度はフェーズ3で測る。

### 実行場所を Skill にした理由

| 案 | 長所 | 短所 |
|----|------|------|
| **隔離環境の Skill + 外での検証 (採用)** | 注入の影響が環境の中で止まる。調査ルールを文章で調整でき、少数の店で試しやすい。店を順番に処理するので同時アクセスを避けられる | 呼び出し間隔を固定できない。Claude Code 経由なので Batches API の割引を使えない。実行環境を用意する必要がある |
| Batches API + スクリプト (全店処理の候補) | トークン料金が50%引き。LLM が使えるツールは `web_search` と `web_fetch` だけで、どちらも Anthropic 側で実行される | 店が並列に処理され、食べログへの同時アクセスを手元で制御できない。1回の試行に時間がかかる。投入、回収、`pause_turn` への対応を実装する必要がある |
| `BackgroundJobs.kt` にジョブを追加 | 既存の仕組みに乗る | 外部ページの読み取りを本番サーバーで行うことになる |

Skill を採用するのは、最初の段階では調査ルールの調整が最も重要だからだ。全店の処理で費用の差が大きければ、Batches API のスクリプトを追加する。判断はフェーズ3の実測で行う。バッチの分け方、調査ルール、`validate-results.mjs` はどちらの方式でも共用する。

Batches API に移す場合は、先に食べログへの同時アクセスを抑える方法を決める。[`web_fetch` が読めるのは会話に既に出た URL だけ](https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-fetch-tool)なので、食べログの検索 URL はスクリプトがプロンプトに入れる。[バッチは24時間以内に終わらないと期限切れになる](https://platform.claude.com/docs/en/build-with-claude/batch-processing)。

### 取り込みファイルの形式

`validate-results.mjs` が出力する `accepted.jsonl` をそのまま使う。1行が1レコードの JSON で、`kind` で種類を区別する。

| `kind` | 主なキー | 管理画面での扱い |
|--------|---------|-----------------|
| `proposal` | `shopId`、`field`、`baseValue`、`proposedValue`、`evidence`、`estimated`、`reviewReasons`、`dedupeKey` | 確認して反映する |
| `notice` | `shopId`、`noticeKind`、`note`、`url` | 店ごとに警告として表示する。提案のない店や反映済みの店も、絞り込みのない未適用の表示に出す |
| `check` | `shopId`、`field`、`outcome`、`checkedAt` | 件数だけ表示する |
| `tag_candidate` | `shopId`、`label` | 集計して、タグ追加の判断に使う |

全レコードに `runId` があり、既定では `b07-2026-11-06` のようにバッチ番号と日付を含む。店名は持たず、画面が本番の店舗から引く。

`accepted.jsonl` は Web 由来の文字列を含むので、利用者の手元に保管し、Git には入れない。適用の根拠をあとで確かめるときはこのファイルを見る。

### 確認画面

管理画面の「調査結果を取り込み」から `accepted.jsonl` を読み込む。ファイルはブラウザの中で読むだけで、1行でも形式が正しくなければ全体を拒否する。

各提案を、本番の現在値と比べて次の3つに分ける。書き出しの後に本番が変わっている可能性があるので、この比較は必須となる。

| 状態 | 条件 | 操作 |
|------|------|------|
| 適用済み | 現在値が提案値と同じ。リンクとタグは既に存在する | 隠す |
| 適用できる | 現在値が `baseValue` と同じ。リンクは同じ種類がまだない。タグは常にここ | 反映、修正して反映、または見送り |
| 食い違い | 現在値が `baseValue` とも提案値とも違う。リンクは同じ種類の別の URL がある | 値を見比べて個別に判断する。一括の対象にしない |

判定を毎回本番の値から導くので、同じファイルを読み込み直しても安全で、途中で失敗したら読み込み直すだけで続けられる。修正して反映した提案は、読み込み直すと元の値のまま食い違いとして表示される。修正の記録を持たないためで、一括の対象にはならない。

- 項目、証拠の種類、`reviewReasons` での絞り込み。
- 現在値と提案値の差分表示、証拠リンク。
- 値を修正して反映する操作。
- 絞り込み結果の一括反映。`reviewReasons` が空の提案だけを対象にする。空になるのは、その店の食べログページ自身を証拠に持つ食べログのリンクだけ。ほかの提案は少なくとも `source_unconfirmed` が付くので、1件ずつ選んで反映する。

反映は店ごとに既存の `updateShop` を呼ぶ。`updateShop` は店舗全体を置き換える API で、`openedAt` と `closedAt` は省略すると消える。そのため、反映の開始時に本番の店舗とタグを読み直し、変える項目だけを差し替えて送る。読み直した時点で、選んだときに画面で見た値から変わっていた提案は反映せず、失敗として表示する。反映のたびに選択を解除するので、もう一度送るには選び直す。タグは slug を本番のタグ ID へ変換する。新しいリンクは編集画面の種別の順で位置を決めて挿入し、既存のリンクの順は変えない。管理者は1人なので、読み直しから保存までの間に別の編集が入る可能性は無視する。

見送りは保存しない。同じバッチは通常1回しか調査しないので、見送った値が戻るのは同じファイルを読み込み直したときだけになる。読み込み直しても反映しなければ何も変わらない。

証拠のメモや店名は Web 由来の文字列なので、プレーンテキストとして表示する。証拠リンクは自動で読み込まず、`rel="noopener noreferrer"` を付ける。

住所は店舗の `address` だけを変える。移転で所在地が変わる場合は座標も変わるので、「移転の可能性」として表示し、既存の編集画面へ誘導する。画面の `address` 対応は、変換スクリプトと一緒にフェーズ2で追加する。

閉店日の時刻は反映で消える。API が日付だけを返し、それを送り直すからで、既存の編集画面でも同じことが起きる。時刻は判断に使わない (「閉店日が不明な店の扱い」を参照)。

## 項目別のルール

調査時に実際に使うルールは `.claude/agents/shop-researcher.md` にあり、機械的に確認できる部分は `validate-results.mjs` が強制する。この章はその背景を説明する。

### 住所

コードで変換し、LLM は使わない。形式は `都道府県市区町村町域 番地 建物名 階` とする。

1. 前後の空白とタブを除き、NFKC で全角数字と全角英字を半角にする。
2. 数字に挟まれたダッシュ類だけを `-` にする。**文字列全体を置換してはいけない。** 試作では `コーポ` が `コ-ポ` に、`らーめん` が `ら-めん` になった。
3. `7丁目13-2` を `7-13-2` にする。数字の直後に別の番地が続くときだけ変換する。
4. `1F`、`１Ｆ`、`1階`、`1f` は `1F` にそろえる。

コードで変換せず、提案に警告を付ける住所がある。

- 地名に数字や `番` を含むもの。`東京都目黒区鷹番`、`香川県高松市番町`、`新潟市中央区西堀通8番町`、`札幌市中央区南6条西4丁目` は地名を変えない。
- 番地が丁目で止まるものや、建物名に丁目を含むもの。`東京都千代田区神田佐久間町2丁目 梅屋ビル`、`京王フレンテ新宿3丁目` など4店ある。
- 町域と番地の間に空白があるもの。`京都市中京区三本木町 462-5 1F` の1店。
- 京都の通り名、漢数字の丁目。`河原町通四条下ル稲荷町二丁目318-6` など。
- 建物欄に店名が混ざるもの。`ら-めんstyleJUNKSTORY`、`口福食堂げん太内` など。
- 都道府県から始まらないもの。`横須賀市大滝町2-4` など4店とタブで始まる1店。

対象外にする店もある。`東京都品川区(住所非公開)` と、米国の `3 Luongo Square, Providence` の2店は変更しない。

食べログの住所が取得できた店は番地を照合し、一致しなければ確認対象にする。

### 店舗リンク

`shop_links.type` の既存の値に割り当て、URL は正規形にして保存する。

| 種別 | 正規形と注意点 | 主な情報源 |
|------|---------------|-----------|
| `official` | 店舗単位のページを優先する。チェーンは店舗ページがなければ公式トップ | Web検索、商業施設のテナントページ |
| `tabelog` | `https://tabelog.com/<都道府県>/<A…>/<A…>/<ID>/`。`ssl.` と `/en/` は除く | 食べログ検索 |
| `twitter` | `https://x.com/<ID>`。`twitter.com` も統一する | 公式サイトのリンク、検索結果のプロフィール |
| `instagram` | `https://www.instagram.com/<ID>/` | 同上 |
| `facebook` | ページの URL | 同上 |
| `reservation` | 予約と整理券をまとめる。言語別 URL は日本語版にする (TableCheck に `/pt/` や `/ru/` がある) | 公式サイト、公式 SNS、予約ページ |
| `other` | LINE、TikTok など | 公式サイト、公式 SNS |

並び順は取り込み画面が編集画面の種別の順で決める (確認画面の節を参照)。店舗あたりの上限は既存の10件に従う。

個人のアカウントや別店舗のアカウントが混ざりやすいので、SNS は次のどちらかを満たすものだけ提案する。公式サイトからリンクされている、プロフィールに店名と地域がある。食べログの公式アカウント欄は根拠にしない。チェーン全体のアカウントは `label` にその旨を書く。

### 食べログの店舗同定

1. 店名で食べログを検索する。`麦笑` の検索では大阪のうどん居酒屋が1位で、正解は2位だった。必ず候補を複数読む。
2. 名前の類似度と住所の番地で判定する。番地が一致すれば同定できたものとする。
3. 複数の候補が残ったら `multiple_candidates` を記録し、食べログのリンクは提案しない。住所が異なる場合も記録し、その店の提案はすべて個別確認にする。

食べログで読むのは同定に使う店名と住所だけで、ほかの値は取らない。

全店に食べログページがあるとは仮定しない。海外店や期間限定の出店は見つからない場合がある。

### 読み

1. 公式サイト、公式 SNS、商業施設のテナントページ、予約ページに読みの表記があれば、ひらがなへ変換する。`トーホーセーソー` は `とーほーせーそー` になる。
2. なければ LLM が推定し、`estimated` の印を付ける。推定は一括承認の対象にしない。難読の屋号は誤読しやすいからだ。

食べログの読みは使わない。公式に読みを書く個人店は少ないと考えられるので、推定の読みが多くなる見込み (推定)。

### 開店日、閉店日、臨時休業

日まで分かる場合だけ提案する。月までしか分からないオープン情報は保存先がないので提案せず、`no_evidence` にする。推測で埋めない。

| 項目 | 認める証拠 | 認めない証拠 |
|------|-----------|-------------|
| 開店日 | 公式の告知、商業施設の開業の告知 | 食べログのオープン日、口コミの初投稿日 |
| 閉店日 | 公式の告知 | 口コミの記述 |
| 閉店の事実 | 公式の告知 | 食べログの閉店表示、Google の営業状態、個人ブログ |
| 臨時休業 | 公式サイト、公式 SNS の投稿、投稿日の記録 | 口コミの記述 |

公式でない情報源だけが閉店を示す店は、値を提案せず `possibly_closed` の警告だけを付ける。確認画面で利用者が公式の情報を探す。食べログの口コミは本文を読まない。`らぁめん鴇` の検索結果には移転に触れた口コミがあったが、店舗の現況の証拠にはしない。

`GLOSSARY.md` の定義に合わせて次のように扱う。

- 臨時休業は1店舗1件なので、終了済みの期間は提案しない。現在と将来の期間だけを提案する。
- 再開日は営業を再開する日で、未定でもよい。
- 閉店店舗には臨時休業を提案しない。
- 閉店日は告知された最終営業日を入れる。既存の値に月末日が多いことからの推定なので、初回の確認時に利用者が確かめる。

### 営業時間

情報源は公式サイト、公式 SNS、商業施設の公式テナントページ、予約・整理券ページに限る。食べログなどのグルメサイト、Google Maps、OpenStreetMap、個人ブログ、口コミは使わない。理由は `docs/adr/0004-business-hours-from-official-sources.md` にある。

- 値の形は API の `BusinessHours` と同じで、`GLOSSARY.md` の営業時間と不定休の定義に従う。週間スケジュールのない店は不定休 (`irregular`) にする。決まった週があって時々休む店は週間スケジュールにし、「ほか不定休あり」を補足に書く。
- 確認日は調査結果に書かせない。`validate-results.mjs` が証拠の `observedAt` の最も新しい日を入れる。
- 現在の値と同じ週間スケジュールでも、確認日が新しければ提案になる。確認画面では「適用できる」になり、反映すると確認日だけが進む。
- 誤った営業時間は利用者を閉まった店へ向かわせるので、すべて `high_impact_field` を付けて個別確認にする。
- 閉店店舗には提案しない。検証スクリプトは、曜日の重複や欠け、時間帯の重なり、第N週の範囲など、サーバーと同じ規則で値を確かめる。最終的な検証はサーバーが行う。

### タグ

2段階で進める。

1. **候補を集める。** 200店ほどについて、LLM に既存タグの判定と、既存タグにない特徴の候補出しをさせる。候補を集計し、追加するタグを利用者が決める。ID、`slug`、`color`、`sort_order` もこの時点で確定する。
2. **決めたタグだけで全店を分類する。** 自由記述は許さない。

タグの性質で扱いを分ける。

| 種類 | 例 | 方法 |
|------|-----|------|
| スープや麺の系統 | 醤油、家系、つけ麺、讃岐 | 公式メニューから LLM が判定。代表的なものを最大3つ |
| 事実から決まるもの | 予約可、予約のみ、朝営業 | 予約欄や営業時間から判定 |
| 主観が入るもの | 行列、老舗 | 自動提案しない。公式が創業年を示す場合のみ老舗を提案 |

「新店」はタグにしない。`opened_at` から導出する既存の方針に従う。

## 手順

各フェーズは完了条件を満たしてから次へ進む。

### フェーズ0: 準備

- 正解データを手で作る。営業店、閉店、うどん、地方、チェーン、住所が不規則な店を混ぜた50店について、正しい食べログ URL、読み、リンクを記録する。
- 「隔離環境の条件」を満たす環境を用意し、`check-isolation.mjs` が終了コード0を返すことを確認する。

完了条件は、上記「利用者が決めること」の2から4が決まり、正解データと隔離環境があること。

### フェーズ1: 取り込み画面 (実装済み)

- 管理画面に `accepted.jsonl` の読み込み、本番との比較、確認、反映の画面を実装した。
- `master` へのマージで Render が自動デプロイする。ファイルを読み込んで反映するまで店舗データは変わらない。

確認は `e2e/tests/admin/shop-enrichment.spec.ts` と `web/src/features/shop-enrichment/` の単体テストで行う。E2E は本物の `validate-results.mjs` の出力を読み込むので、ファイル形式が食い違えば失敗する。提案の反映、適用済みの非表示、`baseValue` 不一致時の食い違い表示、同じファイルの読み込み直しで何も起きないこと、反映しなかった項目が変わらないこと (`openedAt`、`closedAt`、評価、気になる度など) を確かめている。修正しての反映と、画面を開いた後に本番が変わった場合は単体テストで確かめている。

### フェーズ2: 住所

- 住所の変換スクリプトは、同じ `accepted.jsonl` の形式で `field` が `address` の提案を出力する。Web を読まないので隔離環境は不要で、バッチに分ける必要もない。
- 変換規則の単体テストに、上記の例外をすべて入れる。

完了条件は、ランダムな100件の目視で誤変換が0件で、例外以外を一括承認できること。

### フェーズ3: 試験実行と精度確認

- 注入の試験をする。AI 宛の指示と偽の公式アカウントを書いた試験ページを、利用者が管理する公開 URL に置く。その URL を証拠として読ませる。WebFetch は `localhost` を読まないので、公開 URL が必要。不正な値が `accepted.jsonl` の一括承認の対象に入らず、`suspected_injection` が記録されることを確認する。
- 正解データの50店で Skill を実行し、同定とリンク抽出の精度を測る。ここで費用が発生するので、事前に上限額を決める。
- 続けて1バッチを実行し、1店あたりの実費、所要時間、食べログへのアクセス間隔を測る。
- 実費から全店の費用と1バッチの費用を計算し直し、残りのバッチを Skill と Batches API のどちらで処理するか決める。
- 最初のバッチは本番の管理画面から反映し、結果を確かめる。
- 問題なければ残りを1バッチずつ処理する。バッチごとに環境を作り直し、適用してから次へ進む。予算に合わせて止められる。

完了条件は、注入の試験に合格し、同定の精度が正解データで99%以上あり、一括承認の可否を項目ごとに決められること。誤同定は誤ったリンクと読みを連鎖させるので、この値を最も高くする。しきい値は提案であり、測定結果を見て調整する。

### フェーズ4: 読み、店名、日付

- 公式の情報源から読み、開店日、閉店の事実を提案する。公式に読みの表記がない店は推定の読みになる。
- 店名は差分がある店だけ提案する。公式の情報源どうしが食い違う店は両方の証拠を付ける。
- 食べログのリンク以外は一括承認できないので、提案は1件ずつ確認する。

完了条件は、読みの精度が正解データで95%以上あり、店名の提案を全件確認できること。

### フェーズ5: 公式サイト、SNS、予約

- 前のフェーズで埋まらなかった店について、`--fields` で項目を絞って Skill を再実行する。
- 一般のWeb検索は別の店を返しやすい。リンクの提案は個別確認になるので、確認画面でプロフィールの店名と地域を見比べる。

完了条件は、全店で `official`、`twitter`、`instagram`、`reservation` のチェック結果が `found` か `no_evidence` になっていること。

### フェーズ6: タグ

- `--fields tag` で候補の収集 (`tagCandidates`)、タグの確定、全店の分類を順に行う。確定したタグは次のバッチのカタログに入るので、Skill の変更は要らない。

完了条件は、正解データまたは抜き取り100店の確認で利用者が品質を認め、タグを一括承認できること。

### フェーズ7: 反映の確認

反映はバッチごとに済んでいるので、DB の差し替えはしない。最初のバッチを反映する前に手動バックアップを取る。

OGP 画像はハッシュを含むパスで保存される (`og/OgHandler.kt`)。店名や住所が変わった店の画像は再生成される見込みなので (推定)、最初のバッチの反映後に1店確認する。

完了条件は、全バッチの反映後に本番の不足件数を再集計し、確認した内容と一致すること。

### フェーズ8: 継続更新

隔離環境での Skill の実行を定期実行に載せる。実行のたびに次の順で動かす。

1. 信頼する側が、周期を過ぎた店を選んで `batch.json` を作る。`export-batch.mjs` の `--shop-ids` で渡せる。店を選ぶ処理は未実装で、最後に確認した日は過去の `accepted.jsonl` の `check` から分かる。
2. 使い捨ての環境で `/shop-research` を実行する。
3. 信頼する側が結果だけを受け取って検証し、利用者が管理画面に読み込ませる。

実行先は未定で、「隔離環境の条件」を満たせることを基準に選ぶ。候補は Claude Code のコンテナを動かす GitHub Actions の `schedule`、または利用者の PC のタスクスケジューラからコンテナを起動する形。どちらも、データセンターの IP から食べログを読めるかを含めて最初に確かめる。

| 対象 | 周期 | 方法 | LLM |
|------|------|------|-----|
| 公式サイトと予約リンクの死活 | 週1回 | 信頼する側で HTTP を確認。承認済みの URL だけを対象にする | 不要 |
| 公式の情報源の現況 (閉店、移転、店名、アカウント) | 月1回 | Skill | 使う |
| 臨時休業が「再開未定」の店 | 週1回 | Skill | 使う |
| 営業店のうちお気に入り店の臨時休業 | 週1回 | Skill | 使う |
| 上記以外の臨時休業 | 月1回 | Skill | 使う |
| 営業時間の確認日が12か月を超えた営業店 | 月1回、毎回少しずつ | Skill (`--fields business_hours`) | 使う |
| お気に入り店と「絶対行きたい」の店の営業時間 | 確認日から6か月ごと | Skill (`--fields business_hours`) | 使う |

営業時間は全店を1年で一巡させる。営業店1,659店なら月140店ほどで、費用の見積もりの1店あたりの値から月18ドル前後と見込む (推定)。項目を絞るので、実際はこれより少ない見込み。確認日が12か月を超えた店は、店舗詳細に「情報が古い可能性があります」と出る。

`shop-researcher` は x.com と instagram.com のページを直接読まず、検索結果に出た投稿だけを使う。X API は使わない。鍵を隔離環境に置くことになるからだ。臨時休業の検出が検索結果だけで足りるかは未確認なので、この表の運用で確かめる。

反映は常に利用者の確認を経る。定期更新では同じ店を繰り返し調査するので、見送った値が毎回戻ってくる。これが負担になったら、その時点で見送りの記録をサーバーか手元に持つ。

完了条件は、4週間の定期実行で、提案の採用率と月額費用を確認できること。

## 費用の見積もり

すべて推定で、フェーズ3の実測で置き換える。単価は [Anthropic の料金ページ](https://platform.claude.com/docs/en/about-claude/pricing)に基づく。

| 処理 | 想定 (1店あたり) | Opus 5.5 | Sonnet 5.5 |
|------|-----------------|----------|-----------|
| 1店の調査を全店で実施 (Skill) | 入力23,000、出力800トークン、Web検索2回 | 約230ドル | 約130ドル |
| 同じ処理を Batches API で実施 | 同上 | 約135ドル | 約85ドル |
| 1バッチ (50店) を Skill で実施 | 同上 | 約6.4ドル | 約3.6ドル |

- Web検索は1,000回あたり10ドルとして計算した (全店で約36ドル)。Claude Code 経由で同じ料金になるかは未確認。
- Batches API の行は、Skill の行のトークン料金だけを半額にした値。[トークン料金は50%引き](https://platform.claude.com/docs/en/build-with-claude/batch-processing)だが、検索料金に割引が効くかは公式文書に明記がないので、割引なしとした。
- サブエージェントはツールを呼ぶたびに文脈を読み直すので、入力は想定より大きくなる可能性が高い。
- Claude のサブスクリプションで実行する場合は、金額ではなく利用上限が制約になる。
- オーケストレーターの費用はこの表に含まない。各店の結果を文脈に持ち続けるので、1バッチが大きいほど増える。
- 項目を絞ったバッチや、継続更新の一部の店だけなら、この表より少ない。

### 未検証のこと

検証スクリプトは、自動テストと基準データのコピーで確認した。書き出しは、自動テストと本番 API への実行で確認した。全店の書き出しを基準データから作ったものと比べると、違いは基準データの後に統合された2店だけだった。Skill とサブエージェントは隔離環境でだけ動かす前提なので、まだ一度も実行していない。

- `/shop-research` がサブエージェントを1店ずつ呼び、結果をそのまま保存できるか。
- `disable-model-invocation: true` の Skill を `claude -p` から実行できるか。定期実行で必要になる。`--bare` は Skill とサブエージェントの自動検出を止めるので使えない。
- 注入の試験ページに対する実際の挙動。
- WebFetch が robots.txt に従うかは公式文書で確認できなかった。食べログの `robots.txt` は `*` に店舗ページを許可している。
- WebFetch や WebSearch が食べログや検索結果へ届く範囲と、抽出の精度。
- 公式の情報源に読みが書かれている店の割合。
- 閉店店舗や移転店舗が食べログでどう表示されるか。
- X の利用規約は取得できなかった (HTTP 402)。検索結果の投稿を証拠に使う前に確認する。
- 取り込み画面は合成データでだけ動かしている。実際の1バッチで件数と確認の手間が妥当かは、最初のバッチで確かめる。
- Batches API の案は公式文書で確認しただけで、動かしていない。バッチ内の同時実行数を指定できるかは未確認。バッチでの `pause_turn` の扱いは文書の要約で読んだだけなので、実装前に原文を確認する。
